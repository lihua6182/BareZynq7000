## AXI 外设上板调通战役：FPGA_RST_CTRL 之谜 + J-Link/JFlash 三雷（已验证：BRAM 写读回全通）

用户先把 axi_gpio(@0x4120_0000) 换成 axi_bram_ctrl(@0x4000_0000, 8K)，J-Link 实测调通整条链。
（更正：上文"1eaef37 更新 PL 比特流（SmartConnect + AXI GPIO）"的括号标注有误——
该提交里的 81420 B 镜像是 **AXI BRAM** 设计，.bd 19:30 改、impl 19:35 出、19:38 复制转换。）

### 第一层：为什么 GP0 读不到外设（核心 bug，已修）
- 现象：`pl_status=0`（PCAP DONE 断言、看似配置成功），但 0x4120_0000 读全部 "Could not read memory"。
- 排除法取证：板上 flash 的 fpga_img 头（ZBSP/crc）与仓库构建逐字段一致；Vivado .bd 里
  `SEG_axi_gpio_0_Reg @ 0x41200000` 唯一从设备、时钟全 FCLK0、复位全接 `FCLK_RESET0_N` → 比特流/固件/设计三方对齐。
- 根因：**`SLCR.FPGA_RST_CTRL`(0xF8000240) 复位值 0xF，FCLK_RESET0..3 全部有效，固件从未清零**
  → SmartConnect+外设永远蹲在复位里：DONE 照样断言，GP0 访问挂死。FSBL 流程配置完 PL 都会清它，本工程漏了。
- 修复（后续被 fpga_* API 重构收口为 `fpga_reset_release_all()`）：board_init 在 clock_fclk_config 之后
  unlock→`FPGA_RST_CTRL=0`→lock。**修完 0x4000_0000 立即可读**。

### 第二层：调试工具自身埋的三个雷（都已写进 MEMORY.md，此处记事件）
1. **JFlash RAM loader 压扁固件 RAM**：jflash 工程 `RAMAddr=0x20/RAMSize=0x20000`，每次烧写
   SEGGER loader（THUMB 程序）装进低 OCM，覆盖 .data/.bss/`handlers[]`。烧写后 CPU 未经
   reset_handler 恢复 → 残留的 tick 使能 + 垃圾 `handlers[42]`（实测值 0xF04F2300，恰为
   `mov.w r3,#0` 机器码）→ 野跳转 → prefetch abort。**定位手段：handlers 表 dump + addr2line
   解 IRQ LR（=irq_handler zynq_irq.c:48 间接调用点）**。已改 `RAMAddr=0x20000`（栈之上）。
2. **stop-mode 读的注入指令副作用**：读未映射 VA（0xFFFC0238）→ 注入 load translation fault
   → 恢复后固件死于 abort 循环；读无响应 GP0 地址 → 注入 load 永不完成 → 核卡死、halt 失败，
   只能断电。期间板子两次假死、用户配合断电两次。
3. **`r` 假复位**：NORMAL reset 在这套 V13+XC7Z010 上不复位 CPU（寄存器快照跨"复位"全同）。
   软重启用 `h`+`SetPC reset_handler`+`g`（startup 明确支持调试器热复位，重初始化 .data/.bss）。

### 验证结果（最终一轮，写读回）
- `pl_status=0`、jiffies 与等待时长吻合（tick 活）；
- `0x4000_0000` 写 0x12345678 读回一致；`0x4000_1FFC`（8K 顶）写 0xA5A5A5A5 读回一致；中段未写区读 0。

## 中断 tick 不运行的根因定位与修复（已上板验证：LED 正常闪烁）

### 现象
中断式 1ms tick 完全不工作：`tick_mdelay()` 死等、`jiffies` 永远为 0。
此前多轮排查（配/不配 PL、IRQ/FIQ 输入都试、GIC group/target/优先级全调）均无果，
一度被归结为"中断投递路径在该板不工作"（错误结论，已推翻）。

### 真正根因：`.fast` 段从地址 0 起址 → 处理函数地址 = 0 → `irq_attach()` 静默拒绑

- 链接脚本 `scripts/linker/flash_xip.ld`：`.fast` 的 VMA 落在 RAM 段的**最开头**，
  即 `__fast_start__ = 0x00000000`。
- 旧 `zynq_tick.c` 里 `tick_irq` 标了 `section(".fast")`，且 `.fast` 里它排第一个
  → **`tick_irq` 的函数地址恰好是 0x00000000**。
- `irq_attach()` 首行 `if ((id >= NR_IRQS) || (handler == NULL)) return -1;`
  → 0 被判为 NULL，绑定被拒绝（调用处 `(void)irq_attach(...)` 把返回值丢掉了，
  完全静默）。
- 后续 `irq_enable()`、TTC 中断使能照常执行 → 源已使能但分发表 `handlers[42]` 为 NULL：
  - 中断照常投递（当时走 FIQ），TTC 是电平中断、标志无人清 → **FIQ 反复触发**；
  - `jiffies++` 在处理函数里，函数永不执行 → tick 冻结。

### 上板取证（J-Link，供以后复用）
- `handlers[42]`（0x17A8）读出 0；挂接调用反汇编为 `movw/movt r1,#0` → 传参就是 0。
- 连接时 PC 停在 FIQ 向量（FIQ 模式），证明**投递链路是好的**，问题在绑不上。
- TTC0：ISR(+0x54)=1、IER(+0x60)=1、计数器在跑；GIC：ID42 的
  ISENABLER/ISPENDR/ISACTIVER 均置位、ICCICR=0x9（当时 FIQEn=1）。
- `jiffies` 隔 2 秒两次读数都是 0 → 处理函数从未执行。
- 结论：此前"GIC 投递 stalled"的注释是误判，可推翻。

### 修复（本次提交内容）
1. **全部中断改走 IRQ**（不再用 FIQ）：
   - `irq_init()` 写 `GICInterface->CTLR = EnableS|EnableNS|AckCtl = 0x7`，**FIQEn=0**
     （与 Xilinx `XScuGic` 的 `CPUInitialize` 写 0x07 一致）；CPSR 用 `__enable_irq()`
     解 IRQ，FIQ 保持复位屏蔽。
   - 入口函数 `fiq_handler` → `irq_handler`（`interrupt("IRQ")` 属性，需保存 r0-r12）。
   - 源保持 Group 0 + 优先级 + 使能；SPI 补 `GIC_SetTarget(id,1)`（CPU0）。
   - `zynq_irq.c/h` 注释同步更新；`zynq_startup.s` 弱 `fiq_handler` 保留（"fires 即挂"）。
2. **tick 恢复中断驱动**（`zynq_tick.c/h`）：
   - `tick_irq` 不再放 `.fast`（普通 flash 代码，地址 0xFC0010DC），绑定成功。
   - 中断号：TTC0 计数器 0（即 channel-1 寄存器组，偏移 0x000）→ **SPI 42 = `Ttc0Timer0_IRQn`**
     （对 `xparameters.h`：XPAR_XTTCPS_0_INTERRUPTS=0x400a → id 42，一致）。
   - 清标志方式：**读 `INTERRUPT_REGISTER_1`（clear-on-read）**，不是写 1 清零
     （UG585 ch.8 "Interrupt Clear and Acknowledge Sequence"：读即清）。
   - `tick_init()` 检查 `irq_attach()` 返回值，绑定失败就不使能源（避免电平中断风暴）。
   - 掩码用 0x1（interval 位），不再全读。

### 关键硬件事实（核过 UG585/官方驱动）
- ICCICR：bit0 EnableS / bit1 EnableNS / bit2 AckCtl / **bit3 FIQEn**；
  FIQEn=0 → 安全中断走 nIRQ（UG585 Table 7-1）。FIQEn 位 CMSIS 没封装，需手写。
- ICDICFR2 复位值 **0x55555555** = 所有 SPI 高电平有效 → TTC 电平输出天然匹配，
  **不需要** 写 ICFGR。
- TTC 中断寄存器是 clear-on-read（6 bit：bit0 interval / bit1 match0 / ... / bit4 溢出 / bit5 event）。
- TTC0 三个计数器 = SPI 42/43/44（UG585 Table 7-4）。

### 待办 / 潜在坑提醒
- **`.fast` 段首位函数地址仍是 0**（`qspi_clock_init` 在 0x0）。直接调用没事，
  但凡"取地址 + 空指针检查"的注册式接口都绝对不能收 `.fast` 里的函数。
  若日后想根治：把 `.fast` 的 VMA 挪离 0（会顺移 .data/.bss/栈，需整体核对）。
